| **Multi-claim chunk failure → single-claim retry** | [.cursor/plans/multi_claim_batching_ac006a9d.plan.md](.cursor/plans/multi_claim_batching_ac006a9d.plan.md) (Risks section) | When a multi-claim request errors, returns malformed/empty JSON, or returns fewer verdicts than claims, retry the missing claims as individual single-claim batch requests within the same run rather than marking all N as `UNVERIFIABLE no_response=True` (current v1 behavior). **Hard requirement: retry params must match the original multi-claim call byte-for-byte except for `max_tokens`/`max_tool_calls` scaling** — same `model`, same `system` prompt with `cache_control: ephemeral`, same tools list (`web_search_20250305` for Anthropic / `web_search_preview` for OpenAI), same evidence injection policy, same `max_evidence_per_claim`, same temperature/sampling. This preserves prompt-cache parity and keeps single- vs multi-claim quality/cost comparisons clean — without it, retries are silently drawn from a different distribution and muddy the very signal we're collecting this for. Implementation hint: detect inside `reconcile_run` right after `parse_provider_results` (look for verdicts with `no_response=True` and `batch_call_id` matching `*::multi::*`), rebuild a single-claim `BatchDispatcher.submit` against just those claims, splice results into `verdicts_by_claim`. Defer until after first batched SOTU run produces empirical failure-rate data. |
| **Gemini native batch transport** (blocked on Google) | `src/truthbot/verify/batch.py` | **Not an engineering task — waiting on Google.** `google.genai.batches` exists, but it's a Vertex AI-style GCS batch prediction service (GCS input/output buckets, separate service-account credentials) that does **not** support tool calls or GoogleSearch grounding. Grounding is only on synchronous/streaming calls today, so `supports_batch=False` is the correct setting, not a TODO. Current reality: Gemini participates in batch-mode consensus via the **live-sidecar path** (`GeminiAdapter.call()` runs live during submit with full grounding + context caching; verdicts spooled to `metrics/batch_sidecar/<run_id>.jsonl` and merged at reconcile). The only thing we'd gain from a real native batch is the ~50% discount Anthropic/OpenAI get — at the cost of losing grounding, which would tank verdict quality. Reopen when Google ships grounding in their batch tier (or when it's worth maintaining a separate Vertex + GCS credential chain for the price break). |
